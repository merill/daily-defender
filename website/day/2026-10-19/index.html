Day in brief

Defender for Identity sets a 30-day opt-out before sensor v3.x defaults activate

Eligible organizations with an active Defender for Identity workspace receive a banner 30 days before sensor v3.x activation and Windows auditing are enabled by default, including settings currently set to Off. Related guidance separates v2.x and v3.x deployment, migration, connectivity, and account procedures. Defender XDR guidance specifies per-detection-source alert tuning and updates CloudDnsEvents field names. Android guidance clarifies the onboarding and policy sequence, while Message Center item MC1478465 says to disregard its Security Copilot E5/E7 notice because it reached the wrong audience.

  • Identity · Identity protection
    Sensor v3.x activation and Windows auditing get a 30-day opt-out window

    For eligible organizations with an active Defender for Identity workspace, the banner appears 30 days before sensor v3.x activation and Windows auditing are enabled by default, including settings currently set to Off. Selecting Opt out preserves the current settings. The update also records Windows Server 2025 sensor migration support as resolved.

  • Identity · Identity protection
    Sensor v3 migration does not change the action-account setting

    Before migrating, administrators must select and verify “Automatically use the sensor's local system account.” The migration does not change this setting automatically, and leaving gMSA selected can affect response actions.

  • Identity · Architecture and deployment
    In-place v2.x-to-v3.x migration is limited to eligible domain controllers

    The deployment guidance states that in-place migration is currently available only for eligible domain controllers, not other servers, and links to the v2.x requirements and migration prerequisites. Check server roles before planning migration.

  • Defender XDR · General
    Defender XDR alert-tuning guidance specifies per-detection-source selection

    When creating or editing alert-tuning rules, administrators can select individual detection sources within service sources, including include or exclude choices for existing rules. This enables more precise tuning without requiring a stated configuration change.

  • Defender XDR · Hunting and detection
    CloudDnsEvents hunting fields now use EventType and EventSubType

    The table reference replaces DnsEventType and DnsEventSubType with EventType and EventSubType and updates the request-filter example. Existing CloudDnsEvents queries should use the revised column names.
